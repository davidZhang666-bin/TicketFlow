# 五天路线图

日期按北京时间，每天由用户触发。当天验收、文档和推送完成后停止，不提前实现后续模块。

| 日期       | 模块                                                | 验收点                                         | 目标有效提交 |
| ---------- | --------------------------------------------------- | ---------------------------------------------- | -----------: |
| 2026-10-23 | 环境、仓库、CI、认证、活动与时段、基础页面          | 真实依赖启动；活动可创建、编辑、发布和浏览     |       约10次 |
| 2026-10-24 | Redis Lua、预约尝试、订单、限购、幂等、取消与补偿   | 并发不超卖；失败预约可恢复；重复请求不重复扣减 |       约12次 |
| 2026-10-25 | 模拟支付、回调、超时、Outbox 投递、延迟队列、退款   | 锁内裁决付款与超时；迟到付款退款；进程重启恢复 |       约12次 |
| 2026-10-26 | FIFO 候补、递补、退票、活动取消、恢复任务和运营界面 | 无插队；递补超时顺延；批次可恢复；退款独立追踪 |       约12次 |
| 2026-10-27 | 并发看板、k6、故障演练、端到端验收、文档与发布      | 真实吞吐量及延迟报告、库存守恒、截图与 v1.0.0  |       约14次 |

目标约60次实际提交，最低30次，不限制上限。不使用空提交、倒填日期或人为拆碎改动。每次提交应对应可解释的功能、修复、测试、重构或文档。

每天使用 codex/ 功能分支和 PR，合并保留提交历史。未通过的验收项留在当天记录；下一次先补齐，再开展当日模块。依赖系统权限或重启的操作必须如实记录，不把未执行测试记作通过。

## 已确认业务约定

- 一个用户在一个活动内至多有一份有效订单或候补；不同场次共用活动级限购。取消、超时、退票后可重报。
- 每个场次独立库存，每单一份；默认待支付10分钟。
- 候补按数据库顺序自动占位并获得10分钟付款时间，已有候补优先于新报名。
- 以数据库锁内时间判定付款截止。迟到到账记录为支付成功，但不得恢复已失效订单，应自动全额退款。
- 开场前退票，全额退款；资格和库存先失效/释放，退款单独推进。
- 活动取消先关闸，分批结束订单和候补，批量创建退款，支持重试与恢复。
- 支付、退款采用可复现模拟商，保留接入接口；不接真实商户。
- 第五天使用两个 API 与两个 Worker 验证；100名额、10,000请求、最高1,000并发，发布实测环境和结果。
